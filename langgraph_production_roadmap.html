Phase 2

State Deep Dive

Early workflows typically use minimal single-field states:

class JourneyState(TypedDict):
    current_location: str

Production states house multiple distinct fields representing the entire context of execution:

class AgentState(TypedDict):
    user_query: str
    retrieved_docs: list
    tool_result: str
    final_answer: str
    messages: list
Core Rule: Everything important lives inside State.

Program 1: Multi-Field State

from typing import TypedDict

class State(TypedDict):
    user_name: str
    question: str
    answer: str

def chatbot(state):
    return {
        "answer": f"Hello {state['user_name']}"
    }

Production State Topology

State │ ├── messages ├── query ├── documents ├── tool_results ├── final_answer └── metadata
Phase 3

Messages State & Reducers

This is where production LangGraph officially begins. Instead of basic string mappings:

class State(TypedDict):
    question: str

Production graphs rely on an annotated message list with the add_messages reducer:

from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph.message import add_messages

class State(TypedDict):
    messages: Annotated[
        list,
        add_messages
    ]
Why add_messages? LangGraph appends and merges messages automatically. You never need to write manual messages.append() calls. You simply return the delta: 
return {
    "messages": [
        AIMessage(content="Hello")
    ]
}

Program 2: Message State Pattern

from typing_extensions import TypedDict
from typing import Annotated
from langgraph.graph.message import add_messages

This is arguably the most important foundational pattern in all of LangGraph.

Phase 4

The LLM Node

Connecting the LLM (such as ChatGroq) inside a node receiving the message state:

def chatbot(state):
    response = llm.invoke(state["messages"])
    return {
        "messages": [response]
    }
HumanMessage │ ▼ ChatGroq Node │ ▼ AIMessage

Program 3: First Real LLM Graph

START | ▼ Chatbot Node | ▼ END
response = llm.invoke(state["messages"])

This is the inflection point where LangGraph shifts from an abstract state machine to an active AI engine.

Phase 5

Tool Calling

When the model needs live, deterministic, or external information beyond its internal weights:

Direct Model Computation:
User: "What's 500 * 300?"
→ LLM computes directly.
Tool Required:
User: "What's Chennai weather?"
→ Requires real-time external tool.

Tool Definition & Execution Node

def weather_tool():
    return "32°C"

def execute_tool(state):
    result = weather_tool()
    return {
        "tool_result": result
    }

Tool Execution Cycle

User │ ▼ Agent │ ▼ Tool │ ▼ Agent │ ▼ Answer

Production Tool Loop Flow

Human Question ▼ Agent Node ▼ Need Tool? ┌──────────┐ │ YES │ └──────────┘ ▼ Tool Node ▼ Results ▼ Agent Node ▼ Final Answer
Phase 6

Conditional Routing

Dynamically routing execution across specialized nodes based on query semantics:

route_question()
# returns: "web_search" | "calculator" | "chatbot"
if "weather" in query:
    return "weather_tool"

if "math" in query:
    return "calculator"

return "chatbot"

This branching logic serves as the control plane for autonomous AI agents.

Phase 7

Memory & Checkpointing

Beginner In-Memory

messages = []

Production LangGraph Memory

checkpointer = MemorySaver()

graph = graph_builder.compile(
    checkpointer=memory
)

Isolating context and conversation histories across independent user sessions using threads:

config = {
    "configurable": {
        "thread_id": "123"
    }

# The graph automatically recovers and updates state for thread 123
result = graph.invoke(input_data, config=config)
Phase 8

Production Persistence

Moving past ephemeral RAM storage (MemorySaver()) into durable databases:

  • Redis

User ▼ LangGraph ▼ Postgres ▼ History
